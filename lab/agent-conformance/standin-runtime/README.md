# Live-grant stand-in

This value is the lab stand-in for the shell view of every session's live grants. The real route can replace it later because the JSON matches (M1-R).

`StandIn::get_capability_list` answers `GET /api/capability/list`. `scope: None` is the plain route. `scope: Some("all_sessions_live")` is `GET /api/capability/list?scope=all_sessions_live`. The caller is `Shell` or `Client { session_id }`, a method argument for the authenticated session. It is not a JSON field.

A shell caller receives one body on both forms. The body's keys are `scope` and `capabilities`. `scope` is `all_sessions_live`. Each entry's keys are `request_id`, `session_id`, `resource`, `action`, `duration` and `granted_at`. Entries are sorted by `session_id`, then `request_id`.

A client caller with the plain route receives a body whose only key is `capabilities`. Entries are that session only, sorted by `request_id`. Each entry's keys are `request_id`, `resource`, `action`, `duration` and `granted_at`. A client session with no grant receives `capabilities: []`.

`seed_grant` is a lab test seam, not a route. It stores `request_id`, `session_id`, `resource`, `action`, `duration`, the seeded `granted_at`, a life, and `session_ended`. The four lives are `Live`, `Exhausted`, `Revoked` and `Expired`. One filter keeps a grant whose life is `Live`. `session_ended` leaves that grant in the view.

A scope other than `all_sessions_live` is status 400. The reason starts with `unknown capability list scope:` and contains that scope text. A client that asks for `all_sessions_live` is status 403 with the reason `This endpoint requires shell privileges`.

`standin_stopped_run_leaves_no_live_grant`, `standin_cancel_survivor_reaches_running`, `standin_failed_survivor_reaches_running` and `standin_deny_failure_leaves_a_clean_census` satisfy A12's stand-in clause; `standin_a12_census_catches_planted_leftovers` proves the census sees a planted temp dir, API socket and held file. The deny-path `settle_pending` is pinned by `standin_deny_failure_settles_the_sibling_request_and_its_grant_is_refused_through_routes`: removing that call turns it red. `run_leaves_no_live_grant` on the real Runtime stays blocked (`AC-021-GRANTS`) and is a separate row. A passing `standin_` row gives the Runtime no credit.

`StandIn::post_capsules` answers `POST /api/capsules`. `StandIn::get_capsules` answers `GET /api/capsules`. A shell caller receives status 200. A client receives status 403 and the reason `This endpoint requires shell privileges`.

The launch body's only key is `cid`, one printed lab CID. Any other key, `path` included, is status 400 with the reason `resident launch body rejects ` plus that key; a body that is not an object is status 400 with `resident launch body needs cid`, and a `cid` that is not a string or not a printed lab CID is status 400 with that check's own reason. A CID with no admitted row is status 404 with `no bundle is admitted under ` plus the CID plus ` in world ` plus the world name. The launch value's keys are `id`, `name`, `status` and `session_id`. `session_id` equals `id`. The list body's only key is `capsules`. Each entry's keys are `id`, `name`, `status`, `session_id` and `cause`. Entries are sorted by `id`.

The status strings are `starting`, `running`, `stopping`, `stopped` and `failed`. This stand-in stores `starting`, `running`, `stopped` and `failed`. `cause` is empty while `starting` or `running`. A `failed` entry stays while the test-supplied instant is less than 60 seconds after it failed, and the list omits it at 60 seconds. A `starting` or `running` entry stays at every instant.

`admit_resident` takes the bundle path, one `NameSignature`, the explicit accepted publisher list and a `Start`, and stores one row keyed by the bundle's printed lab CID. It walks the bytes on disk with `capsule_identity::checked_bundle` and then checks the signature with `capsule_identity::verify_checked_signature` over the bytes that walk read. The row's name comes from the checked manifest, never from a caller string. A walk refusal is status 400, a signature or name refusal is status 403 with `Refusal`'s own text, and a bundle already admitted under that CID is status 403 with `bundle already admitted: ` plus the CID. A bundle whose checked manifest role is `content` is status 403 with `bundle ` plus its CID plus ` has role content: content opens by CID and never runs as code`; content opens by CID as content and never runs as code, and the check runs on the checked bundle, so the role and the bytes it names are one value. The stand-in has no admission route, so that refusal is proven at this seam, and the launch route then answers 404 `no bundle is admitted under ` plus the CID for it. A refused admission stores no row, creates no instance and mints no grant. A launch re-runs the same check on the bytes on disk, so a bundle changed after admission is status 403 with `Refusal::NameMismatch`'s own text, `bundle bytes name ` plus the new CID plus `; the claim is ` plus the admitted CID. The launch names the instance from the admitted row's checked manifest name, never from the body or a caller string. Admission and a valid signature give identity only: the instance starts `starting` with no grant, and a grant still needs the shell's own `post_capability_grant`. `admit_resident`, `finish_start` and `set_instant` are lab test seams, not routes. `finish_start` is the one call to `resident.start`. Launch answers `starting` before that call returns. An `Error` or `Trap` start stores `failed`, and each `Live` grant whose session is that instance becomes `Revoked` and drops out through the one life filter, as a stop does for its session. A sibling session's grant stays `Live`. The row also keeps the asks the signed bundle declares. `asks.json` sits beside `capsule.json`, so the checked lab CID covers it: the file reads `{"schema": "elastos.agent-host.asks/v1", "asks": [{"kind": <kind>, "resource": <resource>}]}`. This schema is provisional and mirrors the #464 draft. The row keeps the asks that the one checked walk read, and it reads no second file. The file object may hold only `schema` and `asks`, and each ask only `kind` and `resource`. Each refusal is status 400 with its own text: `bundle declares no asks.json` when the file is absent; `asks.json does not follow the provisional ask schema` when the file is not JSON, the schema differs, the file holds no `schema` or no `asks` list, an ask lacks a string `kind` or `resource`, or the list is empty; and `asks.json carries an unknown key: ` plus the key when the file object or an ask holds any other key, the file object's keys first. A refused admission stores no row. A launch re-runs the same check on the bytes on disk, so a changed byte is refused with the same 400 or 403 reason as at admission, and every changed byte leaves the bundle under a new lab CID.
`StandIn::post_capability_request` answers `POST /api/capability/request`. The body keys are `resource`, `action` and `reason`; `action` is lowercased before it is compared. The route stores a request only when one stored ask matches both fields exactly: `kind` equals that lowercased action and `resource` equals the body resource, unchanged. Otherwise it is status 403 with the reason `ask not declared in the signed manifest: ` plus the resource, one space, and the action, and it stores nothing. A prefix, a sibling path and a parent path each fail, because the match is equality. `standin_refuses_a_request_its_signed_manifest_does_not_declare` proves the cases, and `standin_refuses_to_launch_a_bundle_whose_signed_asks_changed` proves that a changed `asks.json` never reaches a guest.

`StandIn::delete_capsule` answers `DELETE /api/capsules/:id`. The body's only key is `reason`. The Ok value is null. `cause` is `stopped: ` joined with that reason. A `stopped` entry stays while the test-supplied instant is less than 60 seconds after the stop, and the list omits it at 60 seconds. Each `Live` grant whose session is that instance becomes `Revoked` and drops out through the one life filter. The sibling instance stays.

`StandIn::get_capability_requests` answers `GET /api/capability/requests?session=`. `session` is the query, a method argument, not a JSON field. A shell caller receives status 200 and a body whose only key is `requests`. Entries are that session only, sorted by `request_id`, with keys `request_id`, `session_id`, `resource`, `action`, `reason`, `status`, `decision_reason` and `settled_by`. A pending entry reads `status` `pending`, `decision_reason` `""` and `settled_by` null. An unknown session reads `{"requests":[]}`. A client caller is status 403 with the reason `This endpoint requires shell privileges`, including when the session is missing. A shell with no session, or an empty one, is status 400 with the reason `requests need a session`.

`seed_request` is a lab test seam, not a route. It stores one pending request and refuses an empty id, session, resource or action, and a repeated `request_id`. The reason may be empty. A stop that the shell accepts denies that session's pending requests through the one settlement function: `status` becomes `denied`, `settled_by` becomes `runtime`, and `decision_reason` becomes the same stop cause. A failed start denies that session's pending requests through the same settlement function, and `decision_reason` is the failure cause. A stop still uses the stop cause, and an `Ok` start does not settle. The request is stored while the instance is `starting`. A record of another session stays pending. The real capability call still returns the grant, so this row gives the Runtime no A11 credit. This value is the lab stand-in and the real route can replace it later because the JSON matches (M1-R). The real A10 row stays blocked.

`StandIn::post_capability_deny` answers `POST /api/capability/deny`. A missing `request_id`, or a body that is not an object, is status 400 with the reason `deny body needs request_id`. `StandIn::post_capability_grant` answers `POST /api/capability/grant`. ## Plan approval (M1 check A15a)

A request may carry `plan`, the `sha256` that `plan_approval::preview` returned; the route stores that hash on the record, and the shell's request view returns it as `plan` (null when the record has none), so the owner reads and approves the same hash the agent requested. `post_capability_grant` takes that hash in `plan_sha256` and refuses a missing or different one with status 403 and the reason `approved plan does not match the requested plan`, leaving the request pending and minting nothing; a `plan_sha256` on a request that stored none is status 400 with the reason `request has no plan to approve`. `post_capability_grant` mints the grant's plan binding from that stored hash, so a binding exists only on a grant the shell approved, and `seed_grant` stores no binding. `mint_plan_binding` and the `PlanBinding` field are private to this module: no crate or test names one. `post_capability_validate` accepts an optional `plan_sha256`. A bound grant authorises its own exact hash alone; any other hash, or no hash, is status 403 with the reason `grant is not bound to this plan`, and the refusal runs before the `once` store, so the grant stays `Live`. The one place `standin_plan_*` tests drive is `post_capability_validate` -> `authorise`. A plan a route cannot honour is refused with a reason: a non-string `plan` is `request plan must be a string`, an unknown `plan*` key is `request body rejects ` plus that key, and a non-string `plan_sha256` is `validate plan_sha256 must be a string`. `standin_plan_approval_spends_the_once_grant_once`, `standin_plan_change_is_refused_and_the_grant_stays_live`, `standin_agent_cannot_approve_its_own_plan` and `standin_plan_preview_is_refused_when_it_is_dropped` in `tests/standin_plan.rs` prove that set. `standin_grant_refuses_an_empty_or_truncated_plan_hash` there proves that an empty approved hash and its first 63 chars are each refused as that same mismatch, mint nothing and leave the request pending, and that the whole hash then mints the bound grant. This value is the lab stand-in and the real route can replace it later because the reason text matches (M1-R). A PASS gives the Runtime no A15b credit.
